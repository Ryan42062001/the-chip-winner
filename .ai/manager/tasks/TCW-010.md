# TCW-010 — Workflow V3.1 Coordination Hardening

ROLE ROUTING: Manager / Architect
STATUS: IN_PROGRESS
EXECUTION MODE: STANDARD_CHAT
DEPENDENCY: INDEPENDENT of TCW-009 production remediation
AUDIT REQUIRED: No independent product audit; exact-head CI and post-merge master verification required.

## Objective

Upgrade the AI-team workflow without changing product behavior.

## Approved scope

1. Establish `ACTIVE_TASKS.json` as the single machine-authoritative operational registry while keeping human-readable summaries secondary.
2. Add explicit `WAITING_EXTERNAL_EVIDENCE` semantics with external actor/action/resume-role metadata.
3. Add `VERIFYING_MASTER` and atomic closeout semantics so merge is not treated as completion.
4. Formalize the reproduced-defect fast lane: Auditor FAIL -> Manager scope -> Builder -> Manager integration -> master verification -> Auditor retest.
5. Standardize a compact verification matrix in meaningful handoffs.
6. Add explicit PR/task supersession metadata and detect duplicate open PRs for the same Task ID when possible.
7. Add an assignment-staleness trigger: active work more than three commits behind requires Full Refresh or target-advancement classification.
8. Add `npm run audit:workflow` and make the existing CI `npm test` gate execute it before the Node test suite.
9. Preserve the five permanent roles, temporary Troubleshooting role, protected PR workflow, evidence hierarchy, and Release 1.0 field gate.

## Constraints

- Do not modify `src/**` product behavior.
- Do not modify `config/field-validation.json`.
- Do not change TCW-009 requirements or Builder implementation scope.
- Keep this task independent of TCW-009 unless actual file/surface overlap appears.
- Workflow audit failures must be deterministic; external GitHub PR lookup failure should warn rather than create a flaky CI failure.
- The current Actions workflow file is not modified by this task. CI enforcement is routed through the existing `npm test` step because repository tooling in this session does not permit editing the workflow YAML.
- Assignment-drift enforcement is strict when the relevant commit history is available. In shallow CI history, inability to resolve historical assignment SHAs must warn rather than falsely fail; Manager/worker refresh discipline remains authoritative for that case.
