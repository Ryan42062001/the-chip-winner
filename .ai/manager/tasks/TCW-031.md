## OBJECTIVE

Reset the Trade Analyzer around an actually usable baseline before V2 intelligence expansion.

Reproduce and repair the current deployed evaluate-a-trade workflow so a user connected to a real ESPN league can:
1. choose a real trade partner;
2. choose one or more outgoing players from the user's selected roster;
3. choose one or more incoming players owned by that selected partner;
4. run the existing read-only consequence analysis;
5. receive a rendered result or an explicit truthful blocked/unknown state rather than a crash, silent no-op, or structurally invalid pseudo-trade;
6. edit/reset/re-run the proposal safely.

Define and preserve the deployed end-to-end UAT contract that must be satisfied before the baseline Trade Analyzer is treated as functional.

## MANAGER-OBSERVED BASELINE DEFECT

Current `src/ui/trade-analyzer.js` builds incoming choices from every snapshot player not on the selected user's roster.

Current `src/domain/trade-analyzer.js` validates incoming players only by:
- existence in the ESPN snapshot; and
- absence from the user's own roster.

The current baseline does not require one counterparty roster to own all incoming players.

As a result, the UI/domain can model structurally invalid "trades" involving:
- free agents / unrostered players;
- players belonging to different opposing managers in one package;
- no explicit trade partner at all.

This defect is accepted as part of TCW-031 scope. It may not be the only end-to-end failure. Builder must still reproduce the complete current workflow and identify any additional directly blocking baseline defects before declaring the implementation ready.

## REQUIRED BEHAVIOR

### A. Explicit counterparty integrity
- A proposal must identify exactly one opposing ESPN team / trade partner.
- The selected partner cannot be the user's selected team.
- Outgoing players must belong to the user's selected roster.
- Incoming players must belong to the selected partner's current roster.
- Free agents / unrostered players must never appear as tradeable incoming assets.
- One proposal may not combine incoming players from multiple managers.
- Changing the partner must clear or revalidate incompatible incoming selections fail-closed.
- Domain validation must enforce the same ownership rules as the UI; UI filtering alone is insufficient.

### B. Baseline package editing
- Support at least 1-for-1, multi-player outgoing, and multi-player incoming packages within the existing Trade Analyzer v1 structural capabilities.
- Proposal controls must remain usable after add/remove/reset/re-analysis.
- Duplicate player IDs remain invalid.
- The same player cannot appear on both sides.
- Follow-up drops remain explicit and only apply when known roster legality requires them.
- Do not silently add waiver/free-agent players as part of the trade.

### C. End-to-end result behavior
- A valid proposal must invoke the existing analyzer and render a deterministic result without uncaught browser errors.
- An invalid/unsupported/incomplete proposal must surface an explicit reason.
- No blank result area, silent click failure, stale result from a previous partner/package, or uncaught exception is acceptable.
- Analysis must remain tied to the currently selected ESPN team and latest loaded snapshot.
- Current/future/playoff source separation and missing-data honesty remain intact.

### D. Real-use visibility
The result must make the evaluated parties/package unmistakable:
- user's team;
- selected trade partner;
- players sent;
- players received;
- any explicit follow-up drop;
- snapshot/source freshness already supported by the current analyzer.

This task may improve labels/control flow necessary to make the baseline understandable, but it must not implement the V2 winner/fairness model reserved for TCW-032/034.

### E. Baseline UAT contract
Create deterministic coverage and a durable acceptance checklist for the deployed workflow.

Minimum future real-deployed UAT:
1. Open Trade Analyzer from a genuine connected ESPN league.
2. Confirm the selected user's roster is correct.
3. Select a real opposing team.
4. Confirm incoming choices contain only that team's rostered players.
5. Build and analyze a genuine 1-for-1 hypothetical.
6. Edit it into a multi-player package and re-run.
7. Switch counterparties and confirm stale incoming selections cannot survive.
8. Confirm a free agent/unrostered player cannot be received as a trade asset.
9. Confirm analysis returns a visible result or truthful evidence limitation without a page error.
10. Confirm no ESPN transaction is sent.
11. Product owner records explicit deployed acceptance/rejection.

Automated tests, CI, deployment smoke, or independent audit do not substitute for step 11.
