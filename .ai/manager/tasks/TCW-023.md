## OBJECTIVE

Implement Trade Analyzer v1 as a production, read-only feature that answers:

> What happens to my fantasy team if I make this proposed trade, and why?

The result must be roster-consequence analysis, not package arithmetic and not a hidden trade-value/winner score.

## REQUIRED PRODUCT BEHAVIOR

Implement the accepted TCW-022 contract, including:

1. **User-entered proposals**
   - one or more outgoing players from the connected user's roster;
   - one or more incoming players from the connected ESPN snapshot who are not already on the user's roster;
   - unequal-count packages such as 2-for-1, 1-for-2, 3-for-2, etc.;
   - explicit optional follow-up drop selection when a known roster-capacity/position rule requires it;
   - explicit team objective: `BALANCED`, `CURRENT_WEEK_STABILITY`, or `FUTURE_UPSIDE`.

2. **Deterministic proposal validation**
   - reject missing/ambiguous player identity, duplicate IDs, a player on both sides, outgoing players not on the user's roster, and incoming players already on the user's roster;
   - do not fuzzy-invent identity;
   - preserve latest connected-snapshot freshness/source context.

3. **Roster consequence construction**
   - build direct and resolved hypothetical post-trade rosters;
   - do not inherit opponent lineup slots for incoming players;
   - do not silently move incoming players to IR;
   - enforce known ESPN active-roster size and finite position limits;
   - return `ROSTER_ACTION_REQUIRED` when a legal final roster needs explicit follow-up removal(s);
   - never silently choose a drop or free-agent add.

4. **Best legal lineup impact**
   - compare pre/post optimized legal starting lineups by approved projection source;
   - expose actual assignment changes, starter/FLEX promotions/displacements, and incoming players who remain bench depth;
   - do not infer immediate starter value from simple player-to-player projection subtraction;
   - current-week numeric direction uses the accepted +/-1.0 projected-point threshold.

5. **Current-week lock semantics**
   - reuse existing lock/kickoff semantics rather than create a competing definition;
   - when realization is locked, current-week output can be informational/counterfactual but must not become an unqualified actionable recommendation;
   - do not claim ESPN trade-processing behavior for locked players.

6. **Depth, contingency, and fragility**
   - expose listed-position depth changes separately from legal contingency coverage;
   - calculate supported `COVERED`, `THIN`, `SCARCE_THIN`, and narrow `DANGEROUS` conditions according to TCW-022;
   - do not make ordinary depth loss automatically fatal;
   - use ESPN replacement/free-agent context only when actually available and attributable to the latest snapshot.

7. **Unequal-count roster-space effects**
   - 2-for-1 consolidation must expose open roster space without auto-adding a free agent;
   - 1-for-2 / extra-incoming packages must expose roster pressure and require explicit follow-up drop(s) when known rules require them;
   - any replacement/add remains a separately labeled conditional follow-up action.

8. **Bye/future/playoff horizons**
   - preserve unknown byes as unknown;
   - compare supported pre/post bye coverage;
   - future weekly comparisons require existing compatibility/identity gates and complete pre/post union-roster coverage;
   - raw `HorizonDelta` is allowed only for complete selected windows;
   - future direction uses `HorizonMeanWeeklyDelta = HorizonDelta / SelectedWeekCount` with `UPGRADE >= +1.0`, `DOWNGRADE <= -1.0`, and `TOSSUP` otherwise;
   - incomplete future coverage is `UNKNOWN`, never zero-filled or extrapolated;
   - playoff aggregate/direction requires explicit playoff weeks plus complete compatible coverage, using the same accepted mean-weekly materiality rule;
   - do not label a partial selected window `REST_OF_SEASON`.

9. **Projection-source separation**
   - evaluate approved compatible sources independently;
   - do not average ESPN and external projections;
   - material disagreement must produce the accepted `SOURCE_DISAGREEMENT` evidence state and source-sensitive wording;
   - FantasyPros ordinal/SOS context must remain separate from projected-point math.

10. **Conclusion precedence**
    Implement the accepted deterministic taxonomy/guards from TCW-022. In particular:
    - narrow `DANGEROUS_POSITIONAL_FRAGILITY` guard remains dominant;
    - `SHORT_TERM_GAIN_LONG_TERM_COST` and `LONG_TERM_GAIN_SHORT_TERM_COST` must be evaluated before generic upgrade/depth labels;
    - `CLEAR_TEAM_UPGRADE` may not hide a supported current-week downgrade or supported long-term `DOWNGRADE`/`MIXED` state;
    - `STARTER_UPGRADE_DEPTH_COST` may not hide a supported long-term `DOWNGRADE`/`MIXED` state;
    - incomplete future evidence is `UNKNOWN`, not a fabricated conflict.

11. **Inspectable output**
    Production behavior must expose equivalent data for:
    - analysis state;
    - proposal sides and team objective;
    - snapshot/freshness context;
    - roster rule status and roster-space consequences;
    - source/horizon-specific pre/post lineup totals and deltas where complete;
    - starter/bench assignment changes;
    - depth/contingency/fragility effects;
    - replacement context when supported;
    - bye/future/playoff effects;
    - source agreement/evidence state;
    - one primary conclusion plus ordered reasons/limitations;
    - explicit read-only semantics.

12. **Production UI**
    - provide an understandable Trade Analyzer entry point in the existing application UI;
    - let the connected user select outgoing and incoming packages without entering private ESPN identifiers manually;
    - support adding/removing multiple players on each side;
    - expose required follow-up drop selection when relevant;
    - expose objective selection;
    - clearly separate proposal controls from analysis results;
    - make roster-space, source disagreement, incomplete evidence, locks, and non-actionable limitations visibly understandable;
    - maintain existing responsive/accessibility conventions.

## REQUIRED DETERMINISTIC COVERAGE

Tests must cover the accepted Strategy scenarios and invariants, including at minimum:

- clear 1-for-1 starter upgrade;
- nominally better incoming bench player with zero immediate lineup gain;
- 2-for-1 starter improvement plus depth/open-slot cost;
- 1-for-2 on a full roster => `ROSTER_ACTION_REQUIRED` until an explicit drop resolves it;
- 1-for-2 with verified existing roster space;
- roster position-limit violation;
- no automatic IR placement;
- supported FLEX/OP eligibility and fail-closed unsupported semantics;
- lock/kickoff informational qualification;
- incomplete current projection coverage withholding numeric team delta;
- source disagreement without averaging;
- complete multiweek aggregate + mean-weekly direction;
- raw multiweek aggregate that is large but mean weekly delta is still `TOSSUP`;
- incomplete future week withholding aggregate/direction;
- complete playoff window;
- incomplete playoff window;
- bye relief with otherwise flat current week;
- ordinary depth loss versus narrow `DANGEROUS` fragility;
- missing ESPN availability remaining unknown rather than weak/empty;
- objective framing changing narrative only, never source facts;
- inverse cross-horizon cases deterministically producing `LONG_TERM_GAIN_SHORT_TERM_COST` and `SHORT_TERM_GAIN_LONG_TERM_COST`;
- no hidden `tradeScore`, winner percentage, acceptance probability, or transaction action.

Add focused domain tests plus UI/browser regression coverage sufficient to prove the user can create, edit, and analyze proposals and can see bounded output states.

## ARCHITECTURAL CONSTRAINTS

- Prefer a dedicated domain module for Trade Analyzer policy rather than burying decision logic in rendering code.
- Reuse existing lineup optimizer, roster rules, lock semantics, waiver/replacement facts, future projection compatibility, bye logic, and season/playoff facts where valid.
- Do not copy policy logic into multiple UI paths.
- Do not weaken existing missing-data/source-separation rules merely to make the analyzer return an answer.
- Keep the feature read-only. No ESPN trade mutation/propose/send/accept/reject code.

- Do not modify `config/field-validation.json` for this implementation task.
