## OBJECTIVE

Remediate the two reproduced recovery defects from TCW-005 without broadening Release 1.0 scope:

1. after a failed authenticated ESPN refresh, preserve the last valid snapshot but durably distinguish it from a newly refreshed/live state across navigation;
2. make refresh-failure guidance truthful for network/fetch failures instead of implying ESPN sign-in is the sole or primary cause.

## REQUIRED BEHAVIOR

### Retained snapshot state

After a live ESPN snapshot has loaded successfully, if a later Refresh ESPN fails:

- keep the last valid ESPN snapshot available;
- do not mutate, replace, or fabricate ESPN source data merely to represent freshness;
- do not fall back to sample/demo data;
- expose a durable application/UI recovery state that clearly communicates that the refresh failed and the displayed data is the last known valid capture, not a newly refreshed live snapshot;
- the durable qualification must remain visible after normal section navigation/render cycles;
- preserve the original capture timestamp/date so the user can understand which snapshot is retained.

A separate application-level refresh/recovery state is preferred over rewriting source snapshot facts, but Builder may use the smallest architecture-consistent implementation that preserves source truth and survives navigation.

### Successful recovery

After connectivity/companion access is restored and a subsequent authenticated Refresh ESPN succeeds:

- clear the failed/stale recovery state;
- restore normal `Live ESPN snapshot` presentation;
- preserve existing successful reconnect behavior;
- keep the product read-only.

### Failure guidance

For a fetch/network-style failure, user-visible guidance must not imply that ESPN sign-in is the only or primary cause when the app cannot establish that classification.

Acceptable behavior includes a bounded message that identifies refresh failure and tells the user to check connectivity, companion availability, and ESPN authentication as applicable, then retry. More specific classification is allowed only when the evidence supports it.

Existing precise companion-health messages (for example, companion not detected/version problems) should not be weakened into a less useful generic message.
