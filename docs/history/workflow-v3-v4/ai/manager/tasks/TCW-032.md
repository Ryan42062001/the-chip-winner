## OBJECTIVE

Define the production-ready strategic contract for the Trade Analyzer V2 winner/value and team-needs layer before Builder implementation.

The contract must make "who wins the trade and why" deterministic, explainable, roster-aware, and testable without turning trade value into a fake probability or hiding uncertainty behind one opaque score.

The policy must support later Builder work for TCW-034 and later team-needs/opportunity work without implementing production code.

## REQUIRED STRATEGY CONTRACT

Define, at minimum:

### 1. Winner / fairness semantics
- Define exactly when the result is `YOU WIN`, `FAIR TRADE`, or `THEY WIN`.
- Define a truthful fail-closed outcome when evidence is insufficient to support one of those labels.
- Define the fairness band and how small edges remain FAIR rather than being overstated.
- Define deterministic precedence when asset-value fairness and user-roster benefit disagree.

### 2. Relative-value interpretation
- Define what an understandable comparison such as 57/43 represents.
- It must be comparative value, **not** probability of success, acceptance, or future performance.
- State whether the displayed split is package value, roster-adjusted utility, or multiple explicitly separated metrics.
- Prevent false precision and hidden cross-source averaging.

### 3. User benefit versus abstract player/package value
- Separate market/package value from the effect on the user's actual roster.
- A fair-value trade that does not improve the user's roster must not be recommended merely because the packages are even.
- Define the do-nothing baseline explicitly: compare the proposed post-trade roster against keeping the current roster.
- Define how a nominal package-value win can still be strategically bad for the user, and vice versa.

### 4. VORP / replacement value
- Define defensible replacement baselines by position using the connected league's actual lineup/roster configuration and legal available-player context where supported.
- Define how replacement quality changes the value of trading away or acquiring a player.
- Preserve the accepted distinction between presentation candidates and the full structurally available pool.
- Do not invent unavailable waiver outcomes or claim an acquisition is guaranteed.

### 5. Positional scarcity
- Define how league size, lineup slots, FLEX/OP eligibility, starter demand, and replacement quality affect scarcity.
- Preserve supported FLEX/OP semantics.
- Avoid double-counting scarcity already represented in VORP/replacement calculations.

### 6. Starting-lineup delta
- Define pre/post optimized starting-lineup comparison.
- Separate true starter improvement from value that remains on the bench.
- Define how unequal packages change lineup occupancy and required follow-up roster actions.

### 7. Depth, fragility, and consolidation
- Define depth value and positional fragility.
- Define how 2-for-1 consolidation can legitimately add value because starting slots are scarce.
- Define how 1-for-2 diversification can add resilience but create roster-space pressure.
- Prevent one large starter delta from silently erasing a material fragility cost.

### 8. Team-needs model
- Define how to identify strongest/weakest starting positions, depth strengths/weaknesses, expendable assets, and priority upgrade areas.
- Define how needs are recomputed after a hypothetical trade.
- Keep "need" roster-specific rather than treating positional ranking alone as a need score.
- Define the minimum deterministic outputs Builder will later need for TCW-035.

### 9. Current / ROS / playoff horizons
- Define separate current-week, rest-of-season, and fantasy-playoff effects.
- Preserve source/horizon separation.
- Define what happens when future/playoff coverage is incomplete.
- Do **not** manufacture or imply that pending `FV-SEASON-01` has passed.

### 10. Confidence / evidence semantics
- Keep evidence confidence separate from winner/value.
- Define confidence inputs such as projection completeness, source freshness, identity mapping, future coverage, and unsupported contingencies.
- Missing evidence must not become negative evidence.
- Define whether low confidence changes wording, suppresses classification, widens fairness interpretation, or triggers a fail-closed result.

### 11. Manager-to-manager plausibility
- Define strategic principles for why the other manager may rationally benefit.
- Consider the other roster's needs/depth without pretending to know preferences that are not observed.
- Do not express this as acceptance probability unless a later calibrated model is separately researched and approved.
- Define what "plausible for both managers" means for future package generation.

### 12. Buy-low / sell-high framing
- Define supported divergence between market/value context and roster utility.
- Do not present buy-low/sell-high as a guarantee of future performance.
- Specify the evidence threshold required before using those labels.

### 13. Roster preferences / untouchables
Define deterministic behavior for at least:
- `DO NOT TRADE`
- `PREFER TO KEEP`
- `ACTIVELY SHOP`

Specify whether each is a hard package-generation constraint, a ranking preference, an explanatory flag, or some combination. Evaluation of a manually entered trade may still describe the consequence of moving an untouchable, but generation must honor the configured constraint.

## REQUIRED DISTINCTIONS

The contract must explicitly distinguish:
- trade value from probability;
- evidence confidence from winner/value;
- user benefit from abstract player/package value;
- fairness from whether the move actually improves the user's roster;
- package fairness from manager-to-manager plausibility;
- source facts from derived strategy;
- current-week evidence from ROS/playoff evidence.

## REQUIRED DETERMINISTIC OUTPUT CONTRACT

Define the minimum Builder-facing output shape or equivalent semantic fields for later implementation. It must cover at least:
- winner classification;
- relative-value comparison or explicit withheld state;
- fairness band;
- do-nothing roster delta;
- starting-lineup delta;
- depth/fragility/consolidation effects;
- VORP/replacement/scarcity evidence;
- team-needs before/after;
- current/ROS/playoff horizon summaries;
- evidence confidence;
- manager-to-manager plausibility explanation;
- plain-language reasons and limitations.

Do not require Builder to infer policy from prose alone. Give deterministic ordering, formulas/thresholds where defensible, explicit tie/unknown behavior, and testable invariants.

## REQUIRED SCENARIOS

Include concrete expected behavior for at least:
1. fair package value but the user's optimized roster becomes worse;
2. `YOU WIN` package value but the user creates a severe positional hole;
3. 2-for-1 consolidation that materially improves a starter slot while reducing depth;
4. 1-for-2 diversification that improves depth but does not change the best lineup;
5. incoming player with strong abstract value but weak roster fit;
6. lower abstract value incoming asset that materially improves the user's biggest need;
7. near-even trade inside the fairness band;
8. materially one-sided trade with high confidence;
9. materially one-sided trade with low/incomplete evidence;
10. current-week gain with ROS/playoff cost;
11. ROS gain with current-week cost;
12. incomplete playoff evidence where no playoff conclusion is allowed;
13. strong replacement pool versus scarce replacement pool for the same outgoing position;
14. FLEX/OP scarcity case where naive position-only VORP would be wrong;
15. `DO NOT TRADE`, `PREFER TO KEEP`, and `ACTIVELY SHOP` behavior;
16. plausible-for-user but implausible-for-opponent package;
17. no worthwhile trade outcome.
